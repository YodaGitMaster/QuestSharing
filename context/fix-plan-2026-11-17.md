
### A2 — Objective step flips between camps on each movement re-plan (with SPF)
- FIXED IN SOURCE: optimizer `options.preferredSites` + `O.siteKey()`; `place()` keeps the held site unless another is cheaper by both `SWITCH_SHARE=0.25` and `SWITCH_SECONDS=20` (`QuestOptimizer.lua` ~:233-266). With SPF, `options.lockSites` holds remembered camps until walking costs arrive. The planner keeps `siteMemory={map,sites}` from the walking-costed solve (or any solve without SPF). A failed estimate or an SPF without `EstimateWalks` lifts the lock. Tests in `tests/test_quest_planner_zone_steps.py`: `..._walking_with_spf_never_flips...`, `..._failed_walking_estimate...`, `..._spf_without_walking_estimates...`, `..._timeline_without_spf_is_unchanged`.
- **SUPERSEDED 2026-11-17 (decouple run r-20261117-234605-6ba9, D5/D7):** `lockSites`, `EstimateWalks` and the walk-costed-only `siteMemory` rule are removed. The planner plans straight-line only; `siteMemory` is written by every solve except for stops whose camp "Camp busy" forced, and is passed as `preferredSites` with or without SPF. The 25 %/20 s margin stays. Step 4's "No-SPF timeline unchanged (switch at 0.56)" no longer holds: `TWO_CAMPS` now gives A,A,A,B,B,B,A,A for 0.50→0.53→0.56→0.65→0.56→0.53→0.44→0.53. The four tests above were replaced by `test_objective_camp_switches_only_when_clearly_cheaper_and_never_flips_back` and `test_spf_is_never_asked_for_walks_and_the_guide_plans_as_without_it`.
```
Root cause      : firstLeg is rebuilt empty each buildRoute (QuestPlanner.lua ~:848) and site choice has no memory,
                  so solve(0) picks the straight-line camp and the SPF re-solve picks the walk-cheaper camp, every re-plan.
Files to change : QuestOptimizer.lua (place), QuestPlanner.lua (planOptions/buildRoute), tests
Steps           : 1. Optimizer option preferredSites = {stopKey -> campKey}; place() keeps the preferred site unless another
                     is cheaper by >= 25 % AND >= 20 s (hysteresis).
                  2. Planner remembers the chosen site per stop.key from the last SPF-costed (or no-SPF) solve, per map.
                  3. When SPF is available, solve(0) locks each stop to its remembered site (if still offered);
                     only the SPF-costed solve may switch, and then only past the hysteresis margin.
                  4. Tests: SPF mock with walk cost 3x and 1.5x to camp A; walk POS 0.50 -> 0.44 -> 0.53 over re-plans;
                     the waypoint never goes A->B->A (it may switch once). No-SPF timeline unchanged (switch at 0.56).
Risk            : too much stickiness keeps a worse camp; margin is a constant, document it.
```

### A4 — Background local search hogs the shared work queue
- FIXED IN SOURCE: `evaluate()` calls `m.checkpoint()` every `YIELD_STEPS=32` simulated actions (`QuestOptimizer.lua` ~:597-620). `refineNeeded` uses a gate: `refinedPlan` inputs (map, stop keys, goal/budget/levelScope/selection/busy camps) plus `REFINE_MOVE=0.1`. quest-costs now runs `solve(0)`, renders, then `refine("quest-improve")`. Tests in `tests/test_data_budget.py`: `test_route_search_yields_at_least_every_64_simulated_actions`, `test_map_search_and_dungeon_scan_keep_half_their_pace_while_the_guide_replans`. Also `test_local_search_gate_holds_when_spf_walking_estimates_never_arrive`.
- **Residual SUPERSEDED 2026-11-17 (decouple run, D5/D6):** the `quest-costs` job is removed (no walking costs exist any more); every route is `solve(0)` → render → `refine()` if `refineNeeded`. `quest-improve` now starts with DataWork priority `"idle"`, so it runs only while no other job can run (map search and dungeon scan keep >= 90 % of their solo pace). `YIELD_STEPS=32` and the `refinedPlan`/`REFINE_MOVE` gate stay. The SPF gate test became `test_local_search_gate_holds_with_any_spf_build`; new `test_route_shows_at_once_then_local_search_follows_with_or_without_spf` and the idle tests in `tests/test_data_budget.py`.
```
Root cause      : evaluate()/remember() replay whole paths without yielding (QuestOptimizer.lua ~:570, ~:633),
                  resumes reach 2.4-3.9 ms; DataWork gives one resume per job per turn, so cheap jobs drop to 5-9 %.
                  quest-improve restarts on every movement rebuild; quest-costs runs the full local search before render.
Files to change : QuestOptimizer.lua, QuestPlanner.lua, tests/test_data_budget.py
Steps           : 1. m.checkpoint() every 32 simulated actions inside evaluate() (covers remember()).
                  2. Start quest-improve only when the stop set changed, the goal/scope changed, or the player moved
                     >= 0.1 map units since the last refined plan; otherwise solve(0) reuses the refined order via preferredIDs.
                  3. quest-costs: solve(0) with walking costs -> render at once -> then refine("quest-improve").
                  4. Test: instrument checkpoints; no optimizer resume runs > 64 simulated actions; vendor-search and
                     dungeon scan keep >= 50 % of solo pumps while the guide refines (harness pump counts).
Risk            : fewer refinements while moving; acceptable (route already stable via preferredIDs).
```

## B — Map search: suggestions while typing (open since v0.4.19)

**Stream B result (2026-11-17): B1–B4 FIXED IN SOURCE** (build_b, review_b approved in round 1). Only `VendorMap.lua` and `tests/test_vendor_map.py` changed.
- B1: a persistent `vendor-index` job (`startIndex`) starts on the first typed character, from OnTextChanged. It runs only if the feature is enabled, not blocked and `Q.canEnumerate` passes. Keystrokes never cancel it; only `resetIndex()` does (disable or provider loss). Its valid() needs `indexToken`, the map shown and a non-empty query. Budget is `FOREGROUND_MS=8` once the user typed; a programmatic `V.search` with no typing keeps the shared 2 ms slice.
- B2: `vendor-search` only matches and hydrates. Spawns stay in `cached` across keystrokes, bounded at `SPAWN_CACHE=2000` NPCs plus the current matches. The cache clears on a map change, on Clear and through `resetIndex`.
- B3: `hydrate()` refreshes suggestions at the first local match and each time the local count doubles. Earlier suggestions stay visible (`keepMatching`). Status shows "Indexing N / M NPCs…", "… items…" and "Finding locations…".
- B4: `test_classic_size_suggestions_arrive_quickly_while_typing` and `test_classic_size_item_query_indexes_items_once_and_suggests_local_items`. CHANGELOG claims about 0.3 s to the first suggestion (was about 3 s) and about 1.4 s for item queries (was about 8 s).
- During build_b, another session's Style.lua restyle changed two `ensureUI` lines (`S.panel(panel)`, `S.inset(edit)`). Both were kept.

```
Root cause      : every keystroke cancels vendor-search and clears resolved/spawns (VendorMap.lua ~:551-562, :179-184);
                  suggestions wait for the WHOLE job (index all NPCs, maybe all items, spawns of all candidates) at the
                  2 ms background slice; refreshSuggestions returns while resolved == nil (:456).
Files to change : VendorMap.lua, tests/test_vendor_map.py
Files NOT to touch : DataWork.lua (use the existing per-job budget argument), Questie.lua
Steps           : B1. Split work: a persistent "vendor-index" job (roles, then items when needed) that keystrokes do NOT
                      cancel, started on the first typed character (never on map open — keeps the no-preload guarantee),
                      with an 8 ms foreground budget while the map is shown and out of combat; pause when hidden.
                  B2. The per-query "vendor-search" job only matches + hydrates candidates; keep hydrated spawns in a
                      bounded cache across keystrokes (do not wipe on each key); clear on map change/provider loss.
                  B3. Incremental suggestions: show local matches as soon as each candidate is hydrated; keep the last
                      suggestions visible until replaced; status shows progress ("Indexing 3,200 / 10,122 NPCs").
                  B4. Budgeted Classic-size test: debugprofilestop mock (4 µs scalar / 10 µs table), 10,122 NPCs /

                      "gene"), <= 0.3 s warm; no catalogue read on map open; all 88 existing checks still pass.
```

  - Follow-up: the code reads the shared menu through `ns._questMenu()`, a test-only accessor in `Menu.lua`, guarded. A proper accessor would need a `Menu.lua` change.
```
Root cause      : QUEST_LOG_UPDATE -> D.refresh() -> ns.closeQuestMenu() (DungeonQuests.lua ~:475-477, ~:611-619).
```
